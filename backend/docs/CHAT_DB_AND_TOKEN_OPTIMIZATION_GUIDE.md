# 채팅 DB 관리 및 API 토큰 최적화 가이드

## 0. 상용급(Cursor급) 기준 정의

상용급(특히 Cursor류)의 컨텍스트 최적화는 **“최근 N턴”**이 아니라, 아래를 동시에 굴린다.

| 영역 | 상용급이 갖추는 것 |
|------|--------------------|
| **메모리 계층화** | 요약 메모리 / 사실 메모리 / 작업 메모리 / 최근 대화 전문을 구분해 관리 |
| **예산 기반 컨텍스트 빌더** | 토큰 예산 안에서 우선순위로 system / memory / retrieved / recent / question 를 채움 |
| **동적 선택(회수)** | 이번 질문과 **관련된** 과거만 검색/랭킹으로 골라 붙임 (최근 N턴 고정이 아님) |
| **중간 요약/압축의 지속 업데이트** | turn-by-turn로 요약을 누적 갱신(덮어쓰기/merge) |
| **캐시/재사용** | 같은/비슷한 입력이면 컨텍스트 빌드 결과·응답 재사용 또는 부분 재사용 |
| **관측 가능성** | 토큰/비용/latency 측정, 품질 저하 감지, fallback(요약 왜곡 시 원본 복구 등) |

## 2. 현재 상태 정리

### 2.1 채팅이 DB로 관리되는 부분 (이미 구현됨)

| 구분 | 저장 위치 | 시점 | 비고 |
|------|-----------|------|------|
| **실제 대화** (유저 메시지 + AI 응답) | `ConversationLog` (conversation_logs) | `POST /api/fortune/chat` 호출 시 | `userInput`, `aiOutput`(JSON 문자열), `elapsedTime`, `isPaid` 저장 |
| 세션 메타 | `FortuneSession` | 세션 생성 시 | `remainingTime`, `expiresAt`, `userData` 등 |

- **채팅 추가**: `ChatFortuneUseCase`에서 AI 응답 생성 후 `ConversationLog.create` → `logRepository.create(log)` 로 DB 저장됨.
- **연관성**: 같은 `sessionId`로 묶여 있어서, `findBySessionId(sessionId)` 로 해당 세션의 전체 대화를 시간순으로 조회 가능.

### 2.2 DB로 관리되지 않는 부분 (근본 원인)

| 구분 | 현재 동작 | 문제 |
|------|-----------|------|
| **초기 가이드** (첫 인사) | `getResultByToken` 호출 시마다 **AI를 호출**해 생성 후, 응답의 `lastChats` 앞에 가상으로 끼워 넣음 | • 결과 페이지 열 때마다 5~15초 지연 • 같은 세션이라도 재조회 시 AI 중복 호출 • DB에 남지 않아 “채팅 이어가기”와 동일한 흐름으로 관리 불가 |

즉, **“채팅 생성/추가”는 DB로 관리되지만, “채팅 시작 시 보여주는 첫 인사(초기 가이드)”만 DB에 없고 매번 API로 생성**하고 있음.

### 2.3 연속성(이전 대화 맥락) — 현재 방식

- **위치**: `ChatFortuneUseCase` → `previousLogs = findBySessionId(sessionId)` → `previousContext` 생성.
- **로직**: `previousLogs.slice(-3)` (최근 3턴)만 사용.
  - 각 턴: `Q: ${log.userInput}\nA: ${log.aiOutput}`.
  - `log.aiOutput`은 **JSON 문자열 전체** (message/summary + points + tips + nextQuestions 등).
- **연관성**: 같은 세션의 최근 3턴을 쓰므로 **연관성은 있음**. 다만 **토큰 수 제한/최적화·선택(회수) 없음**.

### 2.4 토큰 최적화 누락 사항

| 항목 | 현재 | 이슈 |
|------|------|------|
| **previousContext 길이** | 제한 없음. 최근 3턴의 **전체** Q+A 문자열을 그대로 프롬프트에 붙임 | 턴당 aiOutput이 수백~수천 문자(JSON 전체)라 3턴만 해도 입력 토큰 폭증 가능 |
| **토큰 수 제한** | 없음 | 모델별 context limit 초과 위험, 비용·지연 증가. **문자 수가 아니라 토큰 예산**이 상용급에 가까움. |
| **오래된 대화 처리** | 없음. “최근 3개” 고정 | 대화가 길어지면 중간 맥락이 잘림. Cursor는 “요약 누적 갱신 + 최근 N턴 전문”을 **필수 코어**로 둠. |
| **aiOutput 활용 방식** | 전체 JSON 문자열을 A: 뒤에 그대로 포함 | 컨텍스트용으로는 message/summary 한 줄만 써도 되는데 전체를 넣고 있음. |
| **선택(회수)** | 없음 | “이번 질문과 관련된 과거”를 골라 붙이는 로직 없음. |

## 3. 다차원(MDA) 병목 정리

### 3.1 시간 차원: “한 번 생성”은 맞는데, “지속 업데이트”가 약함

- 초기 가이드를 DB에 저장하는 건 **시간 축에서 중복 제거**.
- 대화가 길어질수록 중요한 건 **요약 메모리가 계속 최신 상태로 유지**되는가인데, 현재는 “길어지면 선택적으로 요약”이라 운영 중 품질이 들쭉날쭉해질 수 있음.
- **상용급**: 매 턴마다 최근 대화는 그대로 쌓고, 오래된 대화는 요약으로 흡수하며, **요약은 누적 갱신(덮어쓰기/merge)**.

### 3.2 추상 차원: “대화 로그”와 “기억(메모리)” 분리 부재

- `ConversationLog`는 **증거/감사/리플레이**에 강하고, **메모리**는 **추론 효율/토큰 절약**에 강함.
- **Cursor류**: 원본 로그는 그대로 저장(감사용), **별도 Memory 테이블/필드**에 요약/키팩트/사용자 선호/세션 목표를 저장하고, 프롬프트에는 **Memory 위주**로 투입.
- **현재**: “로그에서 최근 N턴을 뽑아 붙이는 구조”라 **메모리 계층이 약함**.

### 3.3 인과 차원: 지연/비용의 진짜 원인은 “텍스트 양” + “선택 실패”

- 토큰 폭증은 “많이 넣어서”도 생기지만, 더 근본적으로는 **관련 없는 걸 넣어서** 생김.
- **상용급**: “최근 N턴”보다 **“이번 질문과 관련된 과거”**를 더 잘 고름 (Selection).
- **현재 최적화**: **양(Length)을 줄이는 1차 최적화**. Cursor급은 **선택(Selection)을 개선하는 2차 최적화**까지 들어감.

### 3.4 계층 차원: “컨텍스트 빌더”가 제품의 엔진이어야 함

- **상용급**: 컨텍스트 빌더가 **엔진** — 토큰 예산을 받고, 입력 질문을 보고, memory / relevant snippets / recent turns / system rules 를 **우선순위로** 채움.
- **현재**: “최근 N턴 잘라서 붙임”이라 **엔진화가 덜 됨**.

## 4. Phase 1: MVP/실무 최적화 (즉효 · 72→90 체감)

목표: **중복 제거 + 컨텍스트 다이어트** → 비용/지연 즉시 개선, MVP 운영에 최적.

### 4.1 초기 가이드 DB 저장 (18/20)

- **시점**: ASK+CHAT 세션 생성 직후 **또는** `getResultByToken` **최초 1회** (채팅 0건일 때).
- **방식**: AI로 초기 가이드 1회만 생성 → **ConversationLog 1건**으로 저장 (`userInput = ''` 또는 `__initial_guide__`, `aiOutput = JSON.stringify(aiResponse)`). 이후 `getResultByToken`은 **DB만 조회**, AI 호출 없음.
- **구현 시 유의**: “언제 생성(세션 vs 최초 조회)” 정책에 따라 SLA/비용이 갈리므로 운영단에서 결정 후 고정.

**상용급 보강 방향(Phase 2)**  
- 초기 가이드는 **로그 1건**이 아니라 **세션 프리앰블(prelude)** 로 분리 저장 (`FortuneSession.preludeJson` 또는 별도 SessionMemory).  
- 또는 **템플릿 + 변수로 1차 생성(0.1초)** 후, “유저가 첫 질문을 던졌을 때” AI가 자연스럽게 이어받게 해서 **초기 AI 호출 자체를 없애는** 방향도 가능.

### 4.2 previousContext 토큰 제한 · 슬림화 (16/20)

1. **턴 선택**: `findBySessionId` 후 **최근 N턴** (예: N=5). **총 문자 수 또는 추정 토큰 상한** 적용 (예: 2000자 또는 추정 500 토큰 — Phase 2에서는 **토큰 예산 기반** 권장).
2. **각 턴의 “A”**: `aiOutput` 전체 대신 **message 또는 summary 1문장만** 컨텍스트로 사용. 없으면 앞 200자 등으로 자르기.
3. **(선택) 슬라이딩 + 요약**: 오래된 M턴은 1문장 요약, 최근 1~2턴만 Q+A 전문. Phase 2에서는 **필수 코어**로 전환.

**구현**: `buildPreviousContextForAI(logs, options)` 유틸로 분리. 옵션: `maxTurns`, `maxChars` 또는 `maxTokens`(추정), `aiOutputSummaryOnly: true`.

### 4.3 작업 순서 (Phase 1)

| 순서 | 작업 | 설명 |
|------|------|------|
| 1 | **초기 가이드 DB 저장** | getResultByToken 최초 1회(또는 세션 생성 시) AI 1회 호출 → ConversationLog 1건 저장. 이후 조회는 DB만. |
| 2 | **previousContext 슬림화** | 최근 N턴 + 길이/토큰 상한, aiOutput은 message/summary만 포함. |
| 3 | **(선택) 슬라이딩 + 요약** | 대화 길어지면 오래된 턴 요약, 최근 1~2턴 전문. |

## 5. Phase 2: Cursor급 컨텍스트 엔진 (72→88~92)

아래는 **현재 구조를 크게 갈아엎지 않고** 점수를 끌어올리는 **실행 가능한 설계** 12가지.

### 5.1 초기 가이드 · 프리앰블 분리 (1)

- **“초기 가이드”를 로그가 아니라 세션 프리앰블로 분리 저장.**  
- `FortuneSession.preludeJson`(또는 별도 SessionMemory)에 role=system/assistant prelude를 둠.  
- **이유**: 컨텍스트 빌더가 “항상 포함해야 하는 안내문”을 안정적으로 붙일 수 있음.

### 5.2 토큰 예산 기반 구성 (2)

- **maxChars는 근사치라 흔들림.**  
- 토크나이저까지 못 붙이면, 최소한 **대략 토큰 추정 함수(한글 1.5~2.2배 계수)** 라도 두고 **예산으로 자르는** 게 안정적.  
- 모델별 context/요금/지연을 고려한 **토큰 예산**을 인자로 받아, system / memory / retrieved / recent / question 에 우선순위로 채움.

### 5.3 aiOutput 저장 구조 분리 (3)

- 저장 시점에 **“보여주기용 JSON”**과 **“컨텍스트용 텍스트”** 분리.  
- 예: `aiOutputJson`(그대로) + `aiOutputText`(컨텍스트용 1~2문장) + `aiOutputKeywords`(선택).  
- 조회 시 JSON parse 부담과 컨텍스트 빌드 비용이 동시에 줄어듦.

### 5.4 세션 요약 메모리 · 매 턴 업데이트 (4) — 필수 코어

- **FortuneSession.memorySummary**(1~5문단) 같은 필드 1개.  
- **매 턴 끝날 때**, 최근 대화 + 기존 summary를 입력으로 **“요약 업데이트”** 수행 후 저장.  
- 다음 턴 프롬프트에는 **memorySummary + 최근 1~2턴 전문 + 이번 질문** 만 넣어도 토큰이 확 줄고 일관성은 올라감.  
- **“요약이 언제/어떤 규칙으로 업데이트되는지”** 정책을 명시하는 게 핵심.

### 5.5 메모리 2층: Facts vs State (5)

- **Facts**: 사용자 설정, 중요한 배경, 금기, 선호 톤 (변하지 않는 것).  
- **State**: 이번 세션 목표, 최근 결정, 감정 흐름 (지금 문맥).  
- Fortune 상담은 “사실”과 “상태”가 섞이므로, 이렇게 분리하면 요약이 훨씬 안 망가짐.

### 5.6 관련 로그 회수 (6) — Selection

- **최근 N턴 고정 대신**, “이번 질문과 유사한 과거 turn”을 뽑아 붙이기.  
- 임베딩/RAG까지 안 가도 **키워드 매칭 + BM25(또는 간단 TF-IDF)** 로 과거 로그에서 TopK를 뽑아, **최근 2턴 + 관련 2턴** 조합으로 넣어도 체감 품질이 확 올라감.  
- Cursor급의 **선택(Selection)** 쪽 점수를 올려줌.

### 5.7 대화 타입별 컨텍스트 템플릿 (7)

- 연애/사업/금전/건강/결정 등 **타입에 따라** 필요한 memory 필드와 회수 전략을 분기.  
- 토큰은 줄고 정확도는 올라감.

### 5.8 요약 품질 가드레일 · Fallback (8)

- 요약이 누적되면 언젠가 **왜곡**됨.  
- **해결**: summary에 “확신도/출처 turnId”를 남기고, 다음 턴에서 요약 근거가 약하면 **원본 로그 일부를 다시 끌어와 교정**.

### 5.9 컨텍스트 빌드 결과 캐시 (9)

- `buildPreviousContextForAI` 결과를 **sessionId + lastLogId + optionsHash** 로 캐시.  
- 같은 화면에서 재요청/리렌더가 있어도 비용이 거의 0에 가까워짐.

### 5.10 프롬프트 패킷화 (10)

- **system / memory / retrieved / recent / question** 구조를 고정.  
- 디버깅이 쉬워지고, **토큰 예산 초과 시 어느 부분을 줄일지** 자동 결정 가능.

### 5.11 관측(Observability) (11)

- 최소한 아래 5개를 로그/메트릭으로 남기면 최적화가 ‘감’이 아니라 ‘데이터’가 됨.  
  - `inputTokensEstimate`, `outputTokens`, `elapsedTime`, `contextChars`, `retrievedCount`  
- 이후 자동 튜닝(예: N턴 5→3)도 가능.

### 5.12 초기 가이드: 템플릿 1차 생성 + 필요 시 AI 강화 (12)

- 첫 인사를 **매번 AI로 만들지 않고**, 기본 템플릿(운세 타입/사용자 입력값/세션 목적) 조합으로 **0.1초에** 만들고,  
- “유저가 첫 질문을 던졌을 때” 그걸 AI가 자연스럽게 이어받게 하면 **초기 AI 호출 자체를 없애는** 방향 가능.
